## Architectural Decisions

### 1. Task Storage
- **Decision**: Continue using a `list` of `dictionaries` for task storage.
- **Rationale**: This approach successfully managed tasks in Phase-1 and remains simple for Phase-I Intermediate. While a dictionary keyed by task ID might offer faster lookups, the current list size is small, and lookup performance is not a critical bottleneck for a console application. The list maintains insertion order naturally, which is beneficial for default viewing.
- **Alternatives Considered**:
  - **Dictionary keyed by task ID**: Offers O(1) average time complexity for lookups, but complicates maintaining display order (requiring an additional sorting step). Not deemed necessary given the application's scale.

### 2. ID Generation Strategy
- **Decision**: Continue using a simple, incremental integer counter for task IDs.
- **Rationale**: This strategy is straightforward, guarantees unique IDs, and has proven effective in Phase-1. It's perfectly adequate for an in-memory application without concurrent access or distributed concerns.
- **Alternatives Considered**:
  - **UUIDs**: Overkill for an in-memory, single-user console application. Introduces unnecessary complexity and larger ID representation.

### 3. Priority / Tags Representation
- **Decision**: Priorities will be stored as strings ("High", "Medium", "Low"). Tags will be stored as a `list` of strings.
- **Rationale**: This aligns with Python's dynamic typing and dictionary structure. It's simple to implement and manage without introducing custom classes or enums, which would add complexity beyond the project's current scope. Input validation will ensure only allowed priority values are accepted.
- **Alternatives Considered**:
  - **Enum objects for priority**: Would provide stronger type safety and prevent invalid values at the language level. However, for a console app with user string input, this adds a conversion layer and a dependency that might not be in the standard library (though `enum` is standard). The current approach is simpler for input validation.

### 4. Search / Filter Strategy
- **Decision**: Implement iterative search and filtering using list comprehensions and basic string operations on the `tasks` list.
- **Rationale**: For an in-memory list, iterating through tasks is efficient enough for the expected number of items. This approach leverages Python's built-in capabilities and avoids external dependencies or complex data structures like search indices.
- **Alternatives Considered**:
  - **Indexing (e.g., hash maps for tags/priorities)**: Could offer faster filtering for larger datasets but introduces overhead in maintaining indices during task additions/updates, adding unnecessary complexity for an in-memory list of limited size.

### 5. Sort Strategy
- **Decision**: Use Python's built-in `list.sort()` method or `sorted()` function with `key` functions for stable sorting by priority and title.
- **Rationale**: Python's sorting algorithms are highly optimized and stable, naturally handling the specified requirements without needing to implement custom sorting algorithms. This adheres to the principle of "Simplicity Over Abstraction" and leverages the standard library.
- **Alternatives Considered**:
  - **Manual sorting algorithms (e.g., bubble sort, insertion sort)**: Would be less efficient and more complex to implement compared to Python's optimized built-in functions. Not necessary for readability or performance in this context.

## Testing Strategy
Validation will be performed manually based on the acceptance criteria outlined in the `spec.md`.
- **Phase-1 Feature Preservation**: Verify all original Add, View, Update, Delete, Mark Complete, and Exit functionalities from Phase-1 still work correctly.
- **New Feature Functionality**:
  - **Add/Update with Details**: Verify tasks can be added and updated with valid priority and tags. Check invalid priority input.
  - **View with Details**: Verify the `View Tasks` displays the new priority and tags correctly for each task.
  - **Search**: Verify searching by keyword in title returns correct subset of tasks, including no results.
  - **Filter**: Verify filtering by status, priority, and tags returns correct subsets. Test filtering by non-existent tags.
  - **Sort**: Verify sorting by priority (High, Medium, Low) and title (alphabetical) works correctly and is stable. Test sorting on empty lists.
- **Input Validation**: Verify that invalid input (e.g., non-numeric menu choices, empty title, non-existent ID, invalid priority) is handled gracefully with an error message and does not crash the app.
- **Graceful Exit**: Verify the application only exits when the user explicitly selects the "Exit" option.

## Implementation Sections
The `src/main.py` file will be organized into the following logical sections:
1.  **Global State**: Initialize `tasks` and `task_id_counter`.
2.  **Helper Functions**: Utility functions like `find_task_by_id`, `validate_priority`, `parse_tags`.
3.  **Core Operations**: Separate functions for `add_task`, `view_tasks`, `update_task`, `delete_task`, `mark_task_complete`, `search_filter_tasks`, `sort_tasks`.
4.  **Menu Functions**: Functions to `display_menu` and `get_user_choice`.
5.  **Main Loop**: The primary `while` loop that drives the application.
6.  **Application Entry Point**: The `if __name__ == "__main__":` block.
