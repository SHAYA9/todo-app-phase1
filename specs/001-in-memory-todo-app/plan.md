## Architectural Decisions

### 1. Task Storage
- **Decision**: Use a `list` of `dictionaries` to store tasks (e.g., `tasks = []`).
- **Rationale**: This is the simplest and most Pythonic way to manage a small, ordered collection of structured objects without needing custom classes. It aligns with the "Simplicity Over Abstraction" principle.
- **Alternatives Considered**:
  - **Dictionary keyed by task ID**: Rejected because it adds complexity for ordering and iteration, which is a primary view requirement. A list naturally maintains insertion order.

### 2. ID Generation Strategy
- **Decision**: Use a simple integer counter that increments for each new task.
- **Rationale**: This is the most straightforward way to guarantee unique, sequential IDs as required by the spec. It is simple to implement and manage.
- **Alternatives Considered**:
  - **UUIDs**: Rejected as overly complex for a simple, in-memory application. Integer IDs are more human-readable in a CLI context.

### 3. Code Structure
- **Decision**: A single-file script (`main.py`).
- **Rationale**: The application's scope is small enough that a single file is easy to navigate and understand. This avoids premature modularization and adheres to the constitution.
- **Alternatives Considered**:
  - **Modular files (e.g., `model.py`, `view.py`, `controller.py`)**: Rejected as an unnecessary abstraction for this phase. It would increase complexity without providing significant benefit.

### 4. Error Handling Strategy
- **Decision**: Use defensive input validation within the main loop.
- **Rationale**: Check user input (e.g., for menu choices, task IDs) immediately upon entry. This is clear, easy to follow, and prevents invalid data from propagating through the application.
- **Alternatives Considered**:
  - **Exception-driven control flow**: Rejected because it can make the control flow harder to follow for simple validation checks. Standard `try...except` blocks will still be used for type casting (e.g., `int(input())`).

## Testing Strategy
Validation will be performed manually based on the acceptance criteria outlined in the `spec.md`.
- **Startup**: Verify the application starts and displays the menu correctly.
- **Core Actions**: Verify each menu option (`Add`, `View`, `Update`, `Delete`, `Mark Complete`, `Exit`) performs its intended action correctly.
- **State**: Verify tasks are correctly added, updated, and removed from the in-memory list.
- **Validation**: Verify that invalid input (e.g., non-numeric menu choice, empty title, non-existent ID) is handled gracefully with an error message and does not crash the app.
- **Exit**: Verify the application only exits when the user explicitly selects the "Exit" option.

## Implementation Sections
The `main.py` file will be organized into the following logical sections:
1.  **Global State**: Initialize the `tasks` list and the `task_id_counter`.
2.  **Core Functions**: Separate functions for each core operation (e.g., `add_task()`, `view_tasks()`, etc.).
3.  **Menu Functions**: Functions to `display_menu()` and `get_user_choice()`.
4.  **Main Loop**: The primary `while` loop that drives the application.
5.  **Application Entry Point**: The `if __name__ == "__main__":` block to start the application.
