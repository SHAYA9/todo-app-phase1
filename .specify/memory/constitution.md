# In-Memory Python Console Todo Application (Phase I) Constitution

## Core Principles

### I. Spec-Driven Development
The specification is the single source of truth for all development. All code must be generated to meet the spec, and any changes must be driven by spec refinements.

### II. Deterministic Behavior
The application must behave predictably. Given the same sequence of inputs, it must always produce the same output. State changes must be explicit and traceable.

### III. Simplicity Over Abstraction
Prefer clear, simple, and direct code over complex abstractions. YAGNI ("You Ain't Gonna Need It") is a core philosophy.

### IV. Explicit State Management
All application state must be managed explicitly within the in-memory data structures. There shall be no hidden or implicit state.

### V. Zero Manual Human Coding
All Python code for the application logic will be generated by an AI assistant (e.g., Gemini). Human intervention is limited to defining specs, running the generation process, and verifying the output.

## Technical Standards

### I. Technology Stack
- **Language**: Python 3.x
- **Dependencies**: Python standard library only
- **Execution Mode**: Console / Command-Line Interface (CLI)

### II. Architecture
- **Storage**: In-memory only. No file I/O, database, or any form of persistence is permitted in Phase I.
- **Structure**: The application should be a single-file Python script, unless the feature's complexity justifies multiple files and is approved in the spec.

### III. Data Model
- Each task is a dictionary containing:
  - `id`: A unique integer, assigned once and never changed.
  - `title`: A non-empty string.
  - `completed`: A boolean value, defaulting to `False`.
- All tasks must be stored in a single in-memory list.

## Development Workflow

### I. Feature Implementation
1.  **Spec Definition**: A clear, unambiguous spec is written for the feature.
2.  **Code Generation**: The AI assistant generates Python code based on the spec.
3.  **Verification**: The generated code is executed and tested to ensure it meets the spec.
4.  **Refinement**: If the code is incorrect or incomplete, the spec is refined, and the code is regenerated. No manual code edits are allowed.

### II. Action Triggers
- All user actions must be triggered by selecting a numeric option from a displayed menu.
- The application must run in a continuous loop, waiting for user input, until an explicit "exit" command is given.

### III. Input Handling
- All user input must be validated.
- Invalid input or actions must be handled gracefully with a clear error message to the user and must not crash the application.

## Governance

This constitution is the supreme governing document for this project. All development practices, specifications, and generated code must adhere to it.

- **Compliance**: All PRs and reviews must verify compliance with this constitution.
- **Amendments**: Changes to this constitution require a documented proposal, review, and approval. Any approved amendment must be reflected in a new version of this document.
